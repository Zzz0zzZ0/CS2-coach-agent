## 结论

V1 已把原本主要用于社区摘要的 GraphRAG，收敛为可验证的“战队战术分析 + 选手上下文分析”产品链路。统一契约评测 50/50 通过；加入 50 条检索查询后，工程评分为 graph-only 与 hybrid 100.00、vector-only 77.72、community-only 73.76、no-RAG 4.46。

## 数据与验收结果

- 数据范围：5 支队伍、20 场近期比赛、49 张地图、1,030 回合、5,325 个战术 silver labels。
- 图谱规模：48,643 个节点、144,281 条边、20 场比赛、1,023 个有效回合、5,319 个战术序列和 28 个社区摘要。
- 战术查询：30/30 通过；上下文、数值一致性、来源、教练简报、回合下钻、关键回合筛选、胜负对照覆盖率均为 100%。
- 选手查询：20/20 通过；包含总体画像、地图/阵营切片、指定对手切片和双人比较；上下文、数值一致性、来源与回合下钻覆盖率均为 100%。
- 检索延迟：战术查询 p50 332.02 ms、p95 684.07 ms；选手查询 p50 340.79 ms、p95 691.89 ms（本轮开发评测快照，非受控性能对照）。
- 检索集：50 条查询，包括 28 条地图×意图、5 条战队、5 条选手、8 条双语改写和 4 条无答案负例，共 152 个可复算检查点。
- 工程回归：后端测试与前端生产构建通过；浏览器已验证选手自然语言比较、双方证据和回合胜负对照。

## Benchmark 评分

评分只使用本地确定性数据，不调用远程模型：50 个结构化契约用例各计 1 分；正向检索检查是否有结果、地图、意图和可选实体，负例检查是否拒答，共 152 分。总分为 `(契约通过数 + 检索检查通过数) / 202 × 100`。

| 模式 | 结构化契约 | 检索检查 | 总分 |
| --- | ---: | ---: | ---: |
| No RAG | 5/50 | 4/152 | 4.46 |
| Community only | 5/50 | 144/152 | 73.76 |
| Vector only | 5/50 | 152/152 | 77.72 |
| Graph only | 50/50 | 152/152 | 100.00 |
| Hybrid | 50/50 | 152/152 | 100.00 |

No RAG、community-only 和 vector-only 的 5 个契约得分来自正确拒绝 5 条结构化负例；它们无法生成其余 45 条战队/选手结构化答案。修复后，Vector、Graph 与 Hybrid 均通过 50/50 条检索查询。修复内容包括中文战队/战术词展开、无 CS2 领域信号拒答、显式选手实体约束，以及 Graph 的 `match_id` SQL 过滤。Community-only 的 8 个检查失分来自摘要不包含指定战队/选手，而这正是结构化图层需要解决的问题。

## 这些数字证明了什么

它们证明当前 20 场数据上，查询路由、上下文过滤、SQLite 聚合、结构化简报、来源引用和回合下钻之间保持一致；也直接说明结构化图层相较旧社区摘要提供了新增功能，而不是只增加代码量。消融还表明向量检索和结构化图谱是互补关系：前者擅长证据召回，后者负责可计算的战术与选手上下文。

## 尚未证明的部分

- 这不是职业教练人工标注的 gold evaluation，不能证明建议本身达到职业教练质量。
- Silver labels 来自明确规则；其中 Execute Candidate 是弱监督标签，不能当作真实战术意图。
- 指标是描述性统计，不证明某个动作导致胜负。
- 当前样本只覆盖所选 20 场比赛，不能代表队伍的长期版本变化或所有对手。
- 检索标签是由当前 20 场语料的显式事实构建的 silver labels；50 条覆盖可以用于工程回归，但仍不能替代未知赛事上的泛化测试。
- Held-out 仍然共享同一批 20 场底层文档，只隔离了查询和期望；真正的数据分布外评测仍需保留未入库的新比赛。
