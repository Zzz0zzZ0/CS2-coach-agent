# CS2 Coach：工程展示与研究改进路线

本路线基于 2026-09-06 的代码、评测与本地修复验收。下文保留最初方案与当时依据；最新排序与实施状态见 [执行进度](IMPLEMENTATION_PROGRESS.md)。不代表学校招生要求或录取预测。

## 定位

建议定位为“面向 CS2 赛事的可追溯事件分析与受约束教练辅助系统”。核心贡献是把真实 Demo 解析、规则指标、关系检索、来源引用和异步产品串成闭环，并能解释各层的失败边界。当前状态机多数节点确定性执行，模型主要选择训练主题；展示时应准确说明这种设计及成本收益。

求职展示突出独立完成的数据链路、接口、异步任务、测试、可观测性和故障处理。授课型硕士材料可侧重完整工程与清晰的技术总结；研究型硕士材料应进一步形成可检验的研究问题、合理基线和独立实验。院校、专业与申请类型未确定，因此这里不做选校判断。

## 第一项：把问题写成可验证的研究假设

建议研究问题：在保留有答案查询覆盖率的条件下，实体约束与关系证据能否降低 CS2 战术检索的错误回答率，并改善引用支持度？

必须分开呈现三个维度：

1. **检索质量**：在有相关证据的语料上测 Recall@k、nDCG@k、实体/地图/比赛条件准确率；在无答案问题上测误召回率，并同时报告正例错误拒答率。现在的“检索检查通过率”可以保留为工程回归指标，但不应改名为标准 Recall@k。
2. **答案与引用质量**：区分“引用 ID 存在”“引用内容支持该结论”“重要结论都有支持”；现有 Verifier 主要检查格式、引用范围与部分缺失情况，不能当作完整语义验证器。可参考 ALCE 将答案正确性与引用质量分开评估的思路。[ALCE, EMNLP 2023](https://aclanthology.org/2023.emnlp-main.398/)
3. **工程成本**：报告实际模型 input/output tokens、端到端时延、索引时间、存储和失败率。检索 benchmark 的远程模型 token 为零，不等于实际 Coach 请求也为零。

消融应尽量保持语料、过滤条件、返回数量和答案格式一致，比较 BM25、dense、混合文本检索、关系路径检索，再单独开关实体拒答。当前名为 `vector_only` 的模式实际可使用 Milvus dense + BM25，并非纯 dense 基线。当前图层以 SQLite 关系与聚合实现，还应加入直接 SQL 聚合基线，避免把“结构化接口有无”的差异当成图算法优越性的证明。

现有综合分中，Vector-only 缺少 45 条结构化答案契约，因此与 Graph-only 的分差主要说明功能差异。保留该表用于产品验收，但研究主表应采用能力相同的对照。BEIR 提供了跨数据集检验检索泛化、并纳入 BM25 等不同检索方法的参考；本项目无需迁入该框架，只借鉴其评测原则。[BEIR, NeurIPS 2021](https://arxiv.org/abs/2104.08663)

## 第二项：正确设计新比赛评测

现有 held-out 已经揭示过错误类别，修复后的复测应定位为冻结回归验证，不再称为完全盲测。冻结文件未修改很重要，但不足以证明模型或规则从未受到测试信息影响。

第二阶段建议先写协议、再下载新比赛，并区分两种任务：

- **新 Demo 复盘**：历史索引保持冻结，新比赛只作为当前输入。验证解析事实、指标和当前 `[C#]`，历史 `[E#]` 只允许来自旧索引。新比赛未入历史索引时，不应要求检索器返回不存在的该场历史证据。
- **新语料上的检索泛化**：先冻结实现，再对另行保留的新比赛构建独立测试索引；相关证据与标签由新语料产生，开发期间不可见。验证同一套查询和实体规则能否适用于新队伍、选手或比赛，不沿用已调过的查询原句。

按整场比赛隔离，避免同一 BO3 的不同地图或相邻回合横跨开发与测试集。保存比赛/文件哈希、解析器与标签规则版本、索引版本、冻结日期及排除原因。按比赛进行 bootstrap 或分组统计，避免把同场相关回合当成完全独立样本。小规模实验可以先做，但应如实给出区间和样本量，不预设必须达到某个高分才算成功。

## 第三项：验证教练建议是否增加价值

先用现有确定性训练优先级作为基线，与受约束模型选出的优先级比较。相同事实、相同候选主题、隐藏系统名称和输出顺序，由熟悉 CS2 的评审者判断：建议是否被事实支持、是否具体可执行、是否遗漏更重要问题。

建议先抽 30–50 个回合，覆盖胜负、地图、首杀、下包和道具情形，由两名评审独立审阅一部分重叠样本；记录一致率和分歧，而非只给平均主观分。资源不足时可以先做单人抽检，但明确其局限，不称作专家共识。Execute Candidate、同时爆闪归因等不确定标签应单独计分，不能混入“确定事实正确率”。

这一实验既能支持研究叙述，也能回答面试中最关键的问题：为什么需要模型，它相较规则增加了什么？若未体现增益，应保留规则方案并报告负结果。

## 第四项：完善工程证据

当前优先补可复现性，不先拆大文件或增加新框架：

- 将无外部服务的单元测试与依赖 Redis/Milvus 的集成测试区分，所有自动测试默认无真实模型密钥。
- `test_main.py` 当前只断言 Webhook 返回 200 与任务 ID；增加真正检查任务结果、指标和 Verifier 的离线端到端用例。只收到任务不等于分析完成。
- 固定实际可用的依赖版本并验证冷启动；现有前端 lockfile 可用于 `npm ci`，不要无依据重写它。记录 embedding pooling 与模型版本，避免重建索引后发生静默漂移。
- 将本轮已修正的评测非零退出码接入 CI。完整数据 benchmark 可独立手动运行，轻量 fixture 回归应在每次修改时执行。
- 若需要严格控制累计模型开销，先做调用前额度预留与调用后结算，并规定超时导致 usage 未知时的保守记账策略。服务端“额度不足后不重试”无法替代本机累计预算上限。

性能方面先顺序测量，再决定是否批量读取事件、缓存实体集合或拆分图构建与查询职责。当前数据规模不构成引入新的图数据库、消息平台或多代理框架的充分理由。

## 展示与申请材料

建议演示三个闭环：上传 Demo 后得到可核验的复盘；自然语言查询选手并下钻原始回合；未知实体触发拒答，并解释缺少什么证据。每个闭环配一条可复现命令或固定测试输入。

简历与项目摘要可使用“真实比赛数据规模 + 系统职责 + 有限定条件的验收结果”组织，不写“战术正确率 100%”或“达到职业教练水平”。GraphRAG、LangGraph 和 LLM 是实现手段，工程能力体现在可追溯的数据、合理约束、故障处理与实验设计上。

下一阶段的最小组合是：一套公平消融、一批独立比赛验证、一份初始人工审阅和一次干净环境复现。完成后再按目标岗位或具体硕士项目调整叙述重点。
