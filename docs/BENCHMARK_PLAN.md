# 展示材料之前的正式 benchmark 方案

状态：2026-09-07 规划草案，未冻结或执行。目标是判断哪些组件在哪些任务上有价值，而不是预设 GraphRAG 或模型一定胜出。现有实现与失败报告继续保留。

当日执行调整：项目所有者选择由 Codex 审核、少量增加比赛。当前先完成 AI 辅助事实审核并冻结 2 场新系列，不直接启动下述 8–12 场规模。已完成的事后评分、标签身份和新比赛选择见 [AI 审核记录](AI_BENCHMARK_REVIEW.md)。下述独立人工评审仍是更强研究结论所需证据，不是当前工程推进的前置审批。

## 当前证据能说明什么

| 已有产物 | 可支持的结论 | 尚缺的证据 |
| --- | --- | --- |
| 140 项离线测试及 CI | 工程契约、边界与回归可验证 | 不等于检索准确率或建议质量 |
| 16 查询 × 5 方法 × 2 条件 | 同语料实验工具能运行 | 独立相关性标签、足够多的独立问题、语言适配的基线 |
| 1 场新比赛、2 图、44 回合 | 该场解析到报告的链路通过 | 多场隔离测试与任务相关性；这场现在已被观察 |
| 6 图、5 场 Coach 对照 | 真实调用和匿名评分流程可用 | 至少两位独立评审；开发样本不能支撑泛化结论 |

## 要回答的研究问题

| 任务 | 对照 | 主要结果 |
| --- | --- | --- |
| 找到支持问题的回合证据 | BM25、dense、RRF、生产 GraphRAG / Hybrid | 正例 nDCG@10，辅助 Recall@5/10；无答案误召回率与正例误拒答率另报 |
| 理解实体、关系与统计范围 | 同一自然语言输入；显式结构条件只作单列 oracle 参考 | 实体/范围正确率、关系约束满足率、分子分母与空值正确率 |
| 选择有用的复盘重点 | 规则选择与模型选择，共同事实、共同模板 | 独立盲评的优先级适切性分差；可执行性与偏好为辅助结果 |
| 付出的工程成本 | 相同硬件、输入与运行边界 | 端到端 p50/p95、索引构建耗时/大小、每请求 token、失败和降级比例 |

生产 GraphRAG 不能用当前简化的“回合→事件”路径代替。关系任务要包含真实用户会问的动作主体、先后顺序、对手、阵营及跨回合统计，同时保留简单问题，检查图方法在哪些场景没有优势。

## 数据和标签

- 既有 20 场历史语料、旧 held-out、2396950 及 Coach 试跑保持开发/回归身份。先用既有 16 查询完善标签说明和评审工具，不据此宣称独立测试效果。
- 正式测试初步目标为 8–12 场全新完整系列、约 100 个独立语义问题；这是可行性目标，不是样本量或统计效力证明。标注试点后，在正式测试上运行候选方法前冻结最终规模和选择规则。
- 按整场系列隔离，地图不得拆到开发/测试两侧。新比赛测试先明确“在全新比赛组成的隔离索引内检索”，所有方法可访问同一份测试语料；禁止用测试标签调参。它测未见比赛上的表现，不自动等于未见战队或领域迁移。
- 问题覆盖简单事实、关系/时序、画像统计及无答案/范围不存在。预先记录配额；中英文按语义配对并人工核对，翻译版本不当作两个独立样本。多场统计问题应另列任务，避免伪装成属于单场的独立观测。
- 两位独立标注者先看问题和源事实，不看系统排序；在限定的可穷举地图/比赛范围中标出所有相关回合、0–3 等级和事件依据。保留各自原始判断、分歧、仲裁结果和一致性统计。
- 若只能审核候选池，必须报告未标注覆盖率，不能把未审核文档当负例或声称 Recall 使用了完整相关集合。无答案标签必须核查整个限定范围。
- 事实标签可由独立 SQL/核算程序辅助生成，但要区别于人工金标准；抽核原始 Demo，以识别共享解析错误。自由战术建议的价值必须由理解 CS2 的真实评审者判断，模型评分只能作辅助信号。

## 公平对照与消融

- 同一原始事实集合、候选范围、top-k、实体解析器和可用元数据；所有 oracle 条件单列，不能让图方法独享人工正确条件。记录文档表示、分块和输入长度。
- 先在开发集验证中文词法处理。当前 unicode61 BM25 不足以直接代表高质量中文词法基线；当前 128 token 分块均值 MiniLM 也不作为唯一 dense 代表，应补一条开发集验证有效、资源可承受的多语稠密基线。选择和参数必须在正式测试前冻结。
- “共同文本表示的检索算法对照”与“生产系统端到端对照”分开汇报；后者可使用不同表示，但需要披露成本和额外信息，不能只将差异归因于图结构。
- 优先消融实体约束、关系/路径条件、社区摘要和融合策略，每次只去掉一个组件。拒答阈值、top-k、融合参数都只用开发集确定。
- 不预设必须提升某个百分比。保留模型/图方法持平、变差、失败和降级的案例；简单基线表现更好时，应据此缩减系统。

## 汇报与执行顺序

1. 完成标注试点及基线可用性检查，解决自然语言输入与人工结构条件之间的公平性问题。
2. 先冻结比赛选择规则、标签协议、主要指标、代码及预算，再取得新比赛并核对隔离。在正式跑分前冻结最终问题、审核标签与语料/模型哈希。独立标注与开发实现分开管理。
3. 执行离线检索/结构化对照，报告每题原始结果及失败类型。单场任务按比赛组计算配对差值和区间；语言变体和同场地图不能伪装成独立样本。少量比赛的区间只作有限样本描述。
4. 收齐现有 Coach 盲评，确认量表能区分优先级质量，再决定是否扩展到新比赛；不靠增加未评分调用证明增益。事实来自共同模板，不能把共同事实正确归功于模型。
5. 生成主结果表、消融表、质量与成本对照、失败案例及可复现包；注明公开数据的取得方式、哈希、依赖和数据使用限制。然后制作展示材料。

本地检索和规则核算优先，不消耗文本模型额度。模型实验另定调用预算并走现有共享账本，供应商余额快照不自动提高本地上限。没有独立评审时，先交付工程与客观事实评测，人工质量结论保持待评。

方法参考：[BEIR 原论文](https://arxiv.org/abs/2104.08663)强调多样任务上的泛化评估，并发现 BM25 是有力基线。这里借鉴其比较原则，CS2 数据与上述规模均为本项目拟定，不冒称 BEIR 官方评测或已有研究结果。
