# 报告事实核验与当前比赛追问 V1

2026-09-09。借鉴 coding agent 的有限工具调用、预算边界和可解释运行记录，沿用现有 Python、SQLite、FastAPI 与 React；无新增依赖。这里的追问是四类引导式确定性查询，不是开放式聊天代理。

## 报告一致性核验

新版 Verifier 保留引用范围检查，并追加四组 `checks`：从规范化输入重新计算 metrics、核对当前证据的来源标识/元数据/正文、核对 Analyst 固定模板、核对 Coach 固定模板及允许的主题。每组返回状态、检查条目数、不一致数量和最多 20 个路径/原因。任一失败或缺少可验证输入，整体标记 `needs_review`；页面可以展开查看。

这能发现数字、比例、胜方、来源正文、有效但错回合的引用，以及报告和派生指标一同被改动的情况。它复用现有指标算法和渲染模板，属于**确定性报告合同一致性检查**，不是独立事实真值系统。解析器或共享计算逻辑本身的错误仍需独立样本审核，历史证据语义与训练质量未被验证。

同时修复两处事实边界：Coach 的回合引用改按来源顺序生成；首杀/下包胜率以 `known_outcomes` 作分母，保留总 `attempts` 与 `unknown_outcomes`，无已知结果时返回 `null` 并显示胜率不可用。已知结果完整的比赛数字和报告保持一致。缺失或重复的原始回合编号不允许通过新版核验。

## 当前比赛追问

已完成且保存输入的任务支持：

```text
GET /api/tasks/{task_id}/questions?kind=opening_losses
GET /api/tasks/{task_id}/questions?kind=post_plant_losses
GET /api/tasks/{task_id}/questions?kind=round&round_number=13
GET /api/tasks/{task_id}/questions?kind=player&player=huNter-
```

页面在当前报告下方提供同样的四类问题及可展开来源。查询重新读取已保存的解析输入，核对保存时的 SHA256，复用指标计算和来源构建。每次只读取所选比赛；不会将新 Demo 当作已入库历史比赛，也不重跑分析或改写旧报告。

| 边界 | 行为 |
| --- | --- |
| 查询步骤 | 默认且最多 2 步：读取保存输入、查询当前比赛；`max_steps=1` 返回 `budget_exhausted`，无结论或来源 |
| 模型预算 | 0 次；追问服务没有模型、Graph、Redis 或知识摄取调用 |
| 数据范围 | 至多 1,000 个输入回合；统计覆盖全范围，回合来源最多展示 20 条，并显式提示截断 |
| 未知胜负 | 不计作失利；返回未知回合数及范围完整性 |
| 找不到记录 | 完整查询无匹配为 `not_found`；缺少胜负/选手事件为 `unknown`，不推断选手没有参赛 |
| 个人指标 | 精确名称匹配；仅当前输入的有效交战击杀、死亡、首杀，不声称 ADR、综合能力或历史表现 |
| 来源映射 | 引用依照当前证据数组位置；非连续回合编号也能准确对应；重复编号拒答 |
| 非法问题 | 白名单之外、缺失或无关参数返回 422；无本地记录 404，未完成/来源完整性失败 409，存储不可读 503 |

SHA256 用于发现快照意外变更，不提供对拥有本地数据库写权限者的身份认证。工具步骤限制也不是 CPU 时间或内存配额；查询仍需载入当前输入。这一版不持久化追问对话，不执行中断步骤自动续跑。

## 展示与证据边界

追问不需要付费模型调用，现有模型暂停状态维持。原始历史报告与失败运行保持不变；新版本核验只用于新生成的分析，不能将旧版 Verifier 的 `pass` 回填成新验证成绩。

首杀后失利、下包后失利是事件筛选结果，不自动意味着战术决策错误。事实核验和客观工程用例均不能证明建议具有职业教练质量；独立真人质量盲评继续作为后续可选研究。
